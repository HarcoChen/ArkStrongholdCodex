# 战斗观测与多角色 harness 方案（2026-10-30）

状态：`ark_combat` 汇总工具已实现，当前共六个工具；trace、录像、诊断环和多角色仍为设计，不创建子代理或额外玩家。

## 已核对的能力边界

当前 Core 的 `site-worker.mjs` 调用原站引擎，`recordEvents:false`，随后清空 `drainEvents()`；
`rpc.mjs` 只把 `b.start / b.pool / b.end` 转给 Worker。模型的 `view` 来自原生公开／本人私有视图，
不会读取 BattleSpec、种子或未来波次。Huawei 的 JSONL 是决策／状态轨迹，不是逐帧战斗录像。

上游 0.3.3 的 `public/js/battle/metrics.js` 已有 `trackCombat / combineCombat`，
`runner.combatMetrics({scope:'battle'|'last'|'match',ownerId})` 能统计有效伤害、治疗和 DPS/HPS。
这是浏览器模块，不是 `/ws` 查询接口，不能直接给现有 MCP 加一个 RPC 名称就获得统计。
引擎 `Battle.result().perPlayer[*].unitStats` 也有单位伤害／治疗，但口径不应与浏览器统计混用。

上游 `docs/EXTERNAL_AI_ZH.md` 明确把服主侧 external AI / LLM 接入限制在开发分支。
正式发布树通过 `server/release-without-llm` 禁用该路径。本方案继续采用普通玩家 `/ws` 会话；
不把 `SP_EXTERNAL_AI_*` 配置、服主权限或其他席位私有视图带入工具。

## 提议的工具

`ark_combat` 已实现；其余名字和限额仍为工程提案。

| 工具 | 输入 | 输出和边界 |
|---|---|---|
| `ark_combat` | `scope:last|match` | 已结束、本客户端实际模拟战场的玩家／干员伤害、承伤、有效治疗、DPS/HPS 与占比；含联防，标明来源及完整性，不支持 roleId/battleId |
| `ark_trace` | `roleId`, `battleId`, `cursor`, `limit` | 已结束战斗的可见命中／治疗事件分页；不返回 BattleSpec、种子、未来出生队列或隐藏单位 |
| `ark_replay` | `roleId`, `battleId`, `format:json|html` | 导出已保留的本地观测回放，返回受控目录中的文件；HTML 使用记录的帧／事件，不加载任意服务器路径 |
| `ark_diagnostics` | `roleId` | 最近战斗心跳、发送／确认时间、错误和接管原因；无凭据、原始请求头或完整私有数据 |

六个工具保持紧凑。下一决策提示调用 `ark_combat` 复盘，skill 要求每回合结算后、下次操作前调用一次；
不让逐帧消息不断唤醒模型，也不改变 ready 后等待服务端下一决策的屏障。

本次已做统计；诊断和可选 trace／回放仍待后续。帧回放不是 MP4：若需要视频，再由独立渲染器把已保存回放转成视频，
不能仅凭决策 JSONL 声称复现了原始画面。

## 已实现的统计口径

直接读取原生单位 `stats.dmg / taken / heal`，不安装事件观察器、不加载未被内容哈希覆盖的浏览器 metrics 模块，不改变战斗结果。伤害为对敌有效 HP 损失；承伤包含自损／友伤；治疗排除过量及 restore 模式。召唤物沿 owner 链计入干员。玩家占比以已观察战场总量为分母，干员占比以其玩家总量为分母，零分母返回 0。DPS/HPS 按该玩家参与的已记录战场模拟秒数计算。

只有服务端已结算回合可查询：本地提前完成的战斗仍不能提前暴露给模型。`last` 包含该回合普通与联防场，`match` 合并已保留回合；battleId 去重。普通读操作不连接服务器、不推进游戏、不清除动作不确定状态。新开局清空、finish 销毁；最多保留 64 场，返回每玩家最多 256 行干员，省略行不影响总量／占比分母。

返回 `status`、`complete`、逐场 `available/reconstructed/interrupted/reason`、历史淘汰及行省略数量。缺失战场、接管、重建、模拟错误或断联均不能称完整统计。该覆盖范围仅为本客户端模拟的场地（含同场伙伴），不是全队或服务端权威总榜。没有逐帧命中、事件日志或录像。

## 后续事件采集与录像方案

1. 仅在用户明确开启采集后，在每场战斗第一 tick 前安装观察器。优先复用／提取上游统计逻辑并保留许可证，
   通过 `site-loader` 对模块校验哈希；目前 `metrics.js` 不在 sim/shared 内容清单里，不能把“同源”称作内容哈希已覆盖。
2. 伤害采用引擎实际有效 HP 损失；治疗采用实际回复量，排除过量治疗、护盾和元素槽增长。
   召唤物归属沿 owner 链归给干员，同时保留原来源用于解释；避免同一伙伴战场被两个角色重复累计。
3. 记录使用 `matchId + battleId + fieldId + roleId` 唯一键；重连／重新模拟替换同一战斗记录，不叠加两份。
   按玩家统计的时间按其参与的有效战斗时段计算，不简单求和两个并行战场的墙钟时间。
4. 服务端接管以后，原客户端只能提供接管前的观测。返回 `partial:true` 和断点，不能把本地复算或其他角色的完整记录
   默认为原始权威录像。服务器结果、客户端观察、事后复算分别标注来源。
5. 首版只在战斗结束后开放 trace／录像，且仅含本角色可见的快照和事件。原始模拟对象、未揭示状态和未来调度留在 Worker。
   即使 harness 同时持有多个角色，也不自动把它们的私有手牌／商店混入各角色观测。
6. 建议默认仅保存汇总；显式开启后使用每场最多 10,000 条事件、每角色 32 MiB、每 harness 128 MiB 的有界缓冲，
   快照最多 10 Hz。达到限额返回 `truncated:true` 与可用时间范围，不默默丢弃，也不阻塞战斗上报。
   这些限额是待实测调整的工程初值，并非上游规则。
7. 录像导出由宿主写入自己的受控产物目录，路径不由模型任意指定；不访问 Huawei 的任意轨迹文件接口。
   导出的完整观测仍可能包含玩家名字，界面须清楚说明其内容。

## 一个 harness 的多个角色

先区别两种用途：

- 多个子代理协作控制同一席位：共用角色观测，只有席位执行器有写权限；顾问只输出建议，由执行器按 revision 串行提交。
- 一个 harness 占多个席位：每个角色都是独立玩家，必须拥有独立连接、session token、Worker、局面 revision 和取消生命周期。

现状：DSH 已按 `exec.agent` 建立 runtime Map，多个实际 agent 可各有会话；同一个 agent 内仍只有一个角色。
Codex 当前每个 MCP 进程只有一个 runtime，不能假设创建子代理就会自动获得独立身份。
MCP 回调的 sessionId 也不能直接当作子代理身份。若宿主拿不到可信的调用 agent 标识，应由协调器持有角色写权限，
对子代理只转发只读观测与建议；不能把模型自行填写的 roleId 当成权限校验。

建议把 Core 下方的 `RoleManager` 设为共享机制，宿主负责把可信的执行 agent 绑定到 role capability。
键为 `(hostExecutionIdentity, roleId)`；`roleId` 是显式选择的逻辑标识，不作为登录凭据。
一个角色一个 GameClient，每角色最多一个写调用，角色之间允许并发；不能保留当前 Codex 的全局 `busy` 锁。
输出始终携带 `roleId + matchId + epoch + revision`，防止角色重建以后恰好重复的 revision 被误用。

建议增加 `ark_roles` 管理显式创建／列出／关闭角色；其余工具接收 `roleId`。
只有一个角色时兼容旧默认角色，多于一个时禁止省略导致误选。关闭一个角色不影响其他角色。
共享站点认证配置可以继承，但 sessionFile／session token 不能跨角色复用；不能因重复 hello 接管另一个席位。
角色失败／取消只清理自己的待决请求和 Worker，协调器可重绑顾问而不重新创建玩家。

### 房间启动与等待屏障

目前 `ark_start` 只会创建单人局，或加入一个已有房间后挂起等待。这不足以让一个 harness 自己建立多人队伍。
新增明确的房间生命周期接口（例如 `ark_room create|join|ready|start`），或者给现有 start 增加等价的非挂起建房步骤：
先以角色 A 创建 coop 房间并返回房间号，B/C/D 独立加入、准备，再由有房主权限的 A 开始。
房主权限仍由服务器判定。默认不补机器人，不自动开始额外对局。

启动后，协调器必须并发派发各角色的决策等待；不能先 await A 的 ready 结算，再让 B ready，
否则 A 等 B、B 等调度器，形成死锁。各席位按自己的回合发动作，公共轮选仍等服务端 turn。
战斗 Worker 独立运行，模型思考／子代理等待不能暂停上报。

同一 harness 共享内容模块的已校验字节缓存可以降低下载量；各 Worker 的可变 simdata、随机状态、伤害池和会话不能共享。
角色间交流默认只传公开队伍摘要和用户授权共享的信息；若设计集中式全队控制，应显式声明集中观测，
不能在评测中把它和分布式独立观测混成同一口径。

## 验收顺序

- 先验证统计口径：治疗含过量／再生、伤害含 DoT／元素／召唤物、伙伴战场去重；同权重启停观察器不改变战斗结果。
- 再验证完整性：normal/boss/hidden、暂停／恢复、重连、Worker 报错、takeover、缓冲截断和回放结束。
- 多角色先做两席，再做四席：并发 ready 无死锁、角色 A 取消不影响 B、同 session 拒绝、跨角色 revision 拒绝、
  房主退出、轮选、Boss 配对和清理；保留 LLM 来源声明。
- 在工具与凭据隔离完成后，才接入真正的多个子代理；本次不运行这些评测，也不声称能力已经实现。
